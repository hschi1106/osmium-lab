# 回放規格

`osmium-replay` 與 `osmium-runner` 如何把 marketdata 的訊息、模擬委託與策略排成一條決定性的時間線。
設計決策見 [ADR-0008](../design/decisions/0008-full-market-matching-simulation.md) 第 5 點。

狀態：已實作。第 2、3 節在 `osmium-replay`（`MergedFeeds`、`Timeline`），第 4 節以後在
`osmium-runner`。

## 1. 訊息

一則訊息是某個 feed 的一個 `seq`：`books` 的一列、`trades` 的一列，或兩者（`has_trade`）。
訊息的種類與欄位見 [marketdata](marketdata.md)。

| 屬性 | 定義 |
| --- | --- |
| `exch_ts` | 交易所時間，來自資料 |
| `observed_time` | 同一個 feed 中 `seq` 不大於本訊息的所有訊息的最大 `exch_ts` |

`exch_ts` 不保證遞增（暫緩列的時間是暫緩開始的時間），`observed_time` 一定不遞減。
`observed_time` 以整個 feed 計算，與 run 選了哪些商品無關。

## 2. 訊息的全序

依序比較：

1. `observed_time`
2. feed rank：`TWSE_F6` 0、`TPEX_F6` 1、`TWSE_F17` 2、`TPEX_F17` 3、`TWSE_F23` 4、`TPEX_F23` 5
3. `seq`

同一個 feed 內這就是 `seq` 的順序，也就是交易所送出的順序。不同 feed 之間沒有共同的序號，交易所
時間是唯一的依據。

## 3. 時間線

一個 run 的所有事件放在同一條時間線上。每一步從待處理的事件中取 `(時刻, 類別, 序號)` 最小的處理：

| 類別 | 事件 | 時刻 | 序號 |
| --- | --- | --- | --- |
| 0 | 行情訊息在交易所發生：更新 book、撮合模擬委託 | `observed_time` | 第 2 節的全序 |
| 1 | 模擬委託的新單、改單、刪單到達交易所 | 送出時刻 + `latency.order` | 送出的先後 |
| 2 | 回報送達策略 | 產生時刻 + `latency.report` | 產生的先後 |
| 3 | 行情訊息送達策略 | `observed_time` + `latency.market_data` | 第 2 節的全序 |
| 4 | 策略的計時器 | 設定的時刻 | 設定的先後 |

- 策略只在類別 2、3、4 的事件中被呼叫；它在呼叫中送出的委託，送出時刻就是該事件的時刻。
- 新產生的事件，時刻不得早於目前時刻。延遲為 0 時，新事件可能與目前事件同一時刻而類別較小
  （例如策略在類別 3 的事件中送出委託，委託在同一時刻以類別 1 到達）；它就是下一個被處理的事件。
- 委託到達交易所時，所有 `observed_time` 不晚於到達時刻的行情訊息都已經處理完。
- 延遲的定義見[撮合規格](matching.md)第 3 節。

回放時鐘是目前事件的時刻。策略看不到時鐘之後的任何資料。

## 4. 交易日

run 逐一處理日期範圍內的交易日（marketdata `ref/calendar`）。每個交易日：

1. 帳務的開盤前步驟（[帳務規格](accounting.md)第 3 節）。
2. 策略的 `on_day_start`。
3. 當天所有選定 feed 的時間線，直到沒有待處理的事件。
4. 當天仍有效的委託全部失效。
5. 帳務的日結。
6. 策略的 `on_day_end`。

- 交易日的時鐘從 08:30:00 開始：`on_day_start` 與強制委託的通知都在這個時刻。當天有早於
  08:30:00 的行情訊息時 run 失敗（各 feed 的實際資料都不早於 08:30:00）。
- 帳務的強制委託在該盤別開始收單的時刻到達交易所（[撮合規格](matching.md)第 4.3 節），不經過
  `latency.order`：它由券商送出，不由策略送出。
- 第 3 步結束的時刻是當天最後一個事件的時刻。第 4 步的失效回報在那個時刻產生，並在
  `latency.report` 之後送達策略；這些回報與策略因此設定的計時器處理完，當天才結束。
- 第 4 步之後才到達交易所的新委託以 `MarketClosed` 拒絕。
- 委託與計時器不跨日。
- 回報產生時先記入帳務，再排入時間線送往策略。策略收到回報時看到的帳戶，是回報產生當下的狀態
  （[策略介面規格](strategy.md)第 5 節）。
- 交割日由 `ref/calendar` 決定；兩個交易日之間到期的交割在下一個交易日
  的開盤前步驟入帳。
- 交易日缺少選定的 feed（當天的 manifest 沒有這個 feed 的列）時 run 失敗；
  `data.missing_days = "skip"` 時改為記錄診斷並跳過那個 feed 的那一天。被跳過的日子帳務照常進行。
- 每個交易日需要當天與前一個交易日的 `daily` 列（評價與前一日事實）；沒有時 run 失敗。

## 5. 資料品質

- `seq` 有缺口（封包遺失）時照常回放，缺口記錄在輸出中。缺口對撮合的影響見撮合規格第 10 節。
- 讀取前後各比對一次 manifest；資料在 run 進行中被改寫時 run 失敗。
- 遇到規格沒有定義的欄位組合時 run 失敗，不猜測。

## 6. 決定性

輸出只由下列輸入決定：讀到的每個檔案的 manifest identity、設定、策略與 osmium 的版本。相同的輸入
產生位元組相同的輸出；平行處理與衍生快取都不得改變結果。載入是平行的，結果與執行緒數無關
（[效能](../design/performance.md)第 4 節）。
